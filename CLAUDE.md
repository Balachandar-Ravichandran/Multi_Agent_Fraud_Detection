## Environment setup

`chroma-hnswlib` (a chromadb dependency) has no prebuilt wheel for this Python/Windows combo and needs a C++ compiler to build from source — not installed on this machine. Worked around with conda instead of plain `pip`/`venv`:

```powershell
conda create --prefix backend\.venv python=3.12 -y
conda install --prefix backend\.venv -c conda-forge chroma-hnswlib -y
backend\.venv\python.exe -m pip install -r backend\requirements.txt
```

Run ingest with `backend\.venv\python.exe backend\data\ingest.py` (safe to re-run — reference tables use `INSERT OR REPLACE`, the Chroma collection is cleared before each reload). If adding backend deps beyond chromadb, keep using this `.venv`, not a plain-pip one, unless the new dep needs no native build.

## What this is

A multi-agent, retrieval-grounded system that audits vendor invoices against contracts, POs, delivery records, and vendor master data, producing a fraud verdict where every claim traces to a specific document chunk or DB record. Two modes behind one chat endpoint:

- **Audit Mode** — fixed 7-check pipeline, runs on invoice upload.
- **Q&A Mode** — lighter, dynamically-routed follow-up questions scoped to an already-audited case.

A **Preconditions Agent** runs first on every turn (injection defense, mode detection, precondition checks) so neither pipeline guards against malformed/unsafe input itself.

**Non-goals** (do not build): OCR/scanned-doc support, live payment execution, auth/RBAC, a review-queue UI beyond the chat surface, control over PO creation (the contract, not the PO, is ground truth for pricing).

## Tech stack

- Backend: Python (`backend/`) — LangGraph `StateGraph` orchestrator, Pydantic schemas, SQLite (`fraud_system.db`), Chroma (`./chroma_db`) for RAG.
- Models: Claude Sonnet (Plan — high effort, Classifier — medium effort), Claude Haiku (Preconditions, Decide, Act, Validator gates, Summary — low effort).
- Frontend: single-page chat UI (file attach + response rendering) — Node-based per `.gitignore`.
- Logging: single JSONL call site, `core/events.py::emit(category, event, **payload)` → `/logs/run_<id>.jsonl`.

## Rules that aren't obvious from code structure alone

- **All 7 checks always run, in parallel, on every invoice** — a vendor-inapplicable sub-check reports `NOT_APPLICABLE`, never gets skipped/omitted.
- **Confidence formula (`0.6*rule_certainty + 0.4*retrieval_confidence`) applies only when check 7 fires alone.** Checks 1–6 are deterministic facts and collapse to certainty by construction — no confidence math, straight to auto-flag.
- **Gate retries must change something between attempts** — never re-issue an identical deterministic query hoping for a different answer. Gate 2's 3 attempts each change strategy (top_k, query rephrase, then a deterministic metadata filter). Gate 3 only retries on transient technical failure, never on a successful-but-empty result. See Section 9 for the full per-gate table before implementing `agents/validator.py`.
- **Split invoicing vs. legitimate partial shipment**: same vendor + *different* PO refs within 7 days over $10k = flag; same PO ref across invoices = never flagged.
- **Check 7 has an if/else that itself is Decision Point 2** (fraud judgment, not a Validator gate) — distinguishes `PRICE_INFLATION` (price itself exceeds ceiling) from `PO_EXCEEDS_CONTRACT_CEILING` (matches its PO, but the PO was raised above ceiling).
- **Event names are fixed and enumerated** — Section 11 is the single source of truth for all 36 event names/emitting functions. Don't invent new event names or drop specified ones; the grading rubric checks presentation slides against `/logs` against source code for phantom events.
- **Only last-4 bank digits** are ever stored or logged, matching the golden dataset's convention — never persist or print full account numbers.
- **`backend/.env` holds secrets** — never read, print, or commit it.
- **Duplicate billing is chronological, not symmetric**: `storage_tool.lookup_ledger_matches` only matches invoices received *strictly earlier* than the one being checked. Without that, golden-set pair 7001/7002 (identical vendor+PO+amount, 7002 submitted 4 days after 7001) would flag both as duplicates of each other instead of just the later resubmission — this was a real bug caught by the golden-set test, not a hypothetical.
- **Split invoicing only groups invoices that are each *individually* under the $10k threshold** (`checks/split_invoicing.py`) — an invoice already over the threshold alone was never "hiding" from it, so it can't anchor or join a splitting group. This is a refinement beyond Section 7's one-line description, needed to match Section 18's own notes on invoice 1002 and 8001/8002; without it, unrelated large invoices from the same vendor a few days apart (1001, 1004) false-positive.
- **Check 7's contract ceiling and COLA % are parsed from the retrieved clause text itself** (`checks/price_po_contract.py`), not hardcoded per vendor — Apex's contract text grants "up to 3%" COLA, Boltcraft/Meridian's text says none applies, and the regex reads whichever applies from whatever Gate 2 retrieved. Only the *inspection-required* vendor list (`checks/delivery_inspection.py`) and vendor↔contract identity are hardcoded, because the PRD itself names Meridian explicitly for that rule (Section 7).
- **`agents/validator.py::validate()` does not self-emit for `stage="post_rag"`** — every other gate's PASSED/FAILED event is emitted directly inside `validate()` per Section 11's table, but Gate 2's events (`RETRIEVAL_SUCCEEDED`/`RETRIEVAL_LOW_CONFIDENCE`) are attributed there to `checks/price_po_contract.py::retrieve_clause()` instead, under different event names. Don't "fix" this into consistency — it would create a second, uncatalogued emission site for the same judgment.
- **Every check's `run()` takes an optional `run_id: str | None = None`** — omitted (as in all 53 tests), it's pure and silent; passed (as the orchestrator does), it emits `JOB_STARTED`/`JOB_RESULT`/`ANOMALY_DETECTED`/`ANOMALY_DISMISSED_WITHIN_TOLERANCE` per Section 11.3. Keep new checks/tests consistent with this default-off pattern rather than mocking `core.events.emit`.

## Golden dataset (Section 18)

20 invoices, 9 label classes (8 fraud types + `CLEAN`), 6 deliberately adversarial edge cases (1002, 7001/7002, 8001/8002, 9001). `PHANTOM_VENDOR`, `DUPLICATE_BILLING`, `PO_EXCEEDS_CONTRACT_CEILING` each have exactly one example — recall on those is binary, not averaged.
